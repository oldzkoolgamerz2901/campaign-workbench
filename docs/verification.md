### FC2-V1 — stale no-op replacement reports validation failure instead of revision conflict

**Severity: minor; correction required for a clean pass.** In `SessionLibraryService.replace`, when the effective Draft already matches the frozen prepared revision, the new no-op branch checks the request's Draft identity/revision using `Failure.Invalid`. The existing exact-selection guard uses `Failure.Conflict("writing.stale-revision", ...)`. Platform HTTP mapping therefore changes this stale-request case from **409 / `writing.stale-revision`** to **400 / `preparation.library-invalid`**. This violates FC2's requirement to preserve existing revision/conflict semantics while allowing genuine no-op replacements.

Reproduced against the formal bootJar using `/tmp/fc2-contract.sh` and `/tmp/fc2-noop-probe.py`; results are in `/tmp/fc2-contract.log`:

1. Create/save a valid Draft at revision 1 and add it to a session.
2. Send replacement for that exact prepared item with the correct session revision, card key, capture and Draft ID, but request Draft revision 0.
3. Observe HTTP **400** with code **`preparation.library-invalid`**. Session content/revision remain byte-for-byte equivalent at the JSON data level.
4. Send the correct exact revision: HTTP **200**, with the no-op session unchanged.

The rejection is safe; no data loss or unintended replacement was observed. Clients distinguishing conflicts from invalid input receive the wrong error classification. Existing tests cover ordinary stale replacements and exact no-op success, but not stale Draft selection specifically inside this new no-op branch. Relevant source is `backend/src/main/kotlin/workbench/preparation/application/SessionLibraryService.kt:89`–`:90`, compared with `exact` at `:52`–`:55` and the unchanged HTTP failure mapping.

Recommended corrective scope: retain the exact-version no-op behavior and its exemption from the new readiness gate, but use the established revision-conflict classification for mismatched Draft identity/revision. Add an HTTP regression asserting 409/`writing.stale-revision`, no session mutation, and continued correct no-op success. Recheck the affected Preparation/Library and back-text cases. Implementation and subsequent verification require separate owner authorization.
